## 5. 我的工作方式（固定套路）

1. **先读后改**：读相关文件、跑一次现状，确认可复现
2. **先报后动**：涉及结构改动先出清单/方案，得到确认再落代码
3. **小步提交**：一次只搬/改一块，改完立刻跑对应子集
4. **回归兜底**：最后全量 88 项 + 实机跑关
5. **留证据**：审查记录、搬迁清单、截图、日志都写进 `docs/`
6. **可回滚**：改动集中、注释说明，必要时能单独撤销

## 6. 边界与限制

- **不能**：绕过审批弹窗（已禁用）、装未知来源的驱动/内核级软件、替你注册需要验证的第三方账号、访问需要手机验证的页面
- **网络**：Google/Gemini 网页需代理；本机代理已配好，但账号地区限制我无法绕过
- **费用**：生图/生音频/Scenario 都消耗真实额度；我会先报成本再批量
- **破坏性操作**：删除/移动文件前必须先核对绝对路径；涉及素材替换会先问
- **耗时**：全量回归约 8–10 分钟，十关实机约 35–40 分钟；长任务我会后台跑并汇报

## 7. 给 GPT 的下单模板（建议）

每个任务按这个结构给我，我就能独立跑完并交付：

```markdown
### 任务：<一句话目标>
- 范围：<要改的文件/模块；不要动的部分>
- 验收：<可执行的判定，如"88 项回归全绿"、"L7 通关且用时 ≤ 320s">
- 约束：<不许改的接口/资源；必须保留的行为>
- 交付：<审查记录 / 搬迁清单 / 截图 / 代码 diff 说明>
- 优先级：P0/P1/P2
```

**示例**

```markdown
### 任务：拆分结算页
- 范围：battle_ui.gd 的 _fill_result 与结果按钮逻辑 → kushou/result_view.gd
- 验收：result_panel / result_freeze / battle_lifecycle 全过；全量 88 绿；结算截图与改前一致
- 约束：结果页布局与按钮文案不变；_end_run 的流程不变
- 交付：搬迁清单 + 前后截图 + 回归日志路径
```
